# Task 260: Notification UI & Configuration

## Description

Implement user-facing notification configuration UI, enabling users to control notification settings, configure reminder preferences, and manage notification permissions. This task bridges the backend NotificationService (#176) with user controls, making notifications fully functional.

**Critical Gap Addressed:** Issue #176 implemented the NotificationService backend (scheduling logic, queue management, action handling) but provided no UI for users to enable/configure notifications. ### 3. NotificationService Activation

**Extend NotificationService.swift:**

Add public activation methods called from settings:

```swift
// NotificationService.swift - Add these methods

/// Enable notifications and schedule reminders for all active schedules
public func enable() async throws {
    // 1. Check/request authorization
    let granted = try await requestAuthorization()
    guard granted else {
        throw NotificationServiceError.authorizationDenied
    }

    // 2. Refresh notification queue for all active schedules
    try await refreshNotificationQueue()

    // 3. Set background refresh task
    scheduleBackgroundRefresh()

    // 4. Update enabled state
    notificationsEnabled = true
}

/// Disable notifications and cancel all pending reminders
public func disable() async {
    // 1. Cancel all pending notifications
    await notificationCenter.removeAllPendingNotificationRequests()

    // 2. Clear notification queue
    notificationQueue.removeAll()

    // 3. Update badge count
    await updateBadgeCount()

    // 4. Update enabled state
    notificationsEnabled = false
}

/// Update reminder timing preference and reschedule notifications
public func updateReminderTiming(_ minutes: Int) async throws {
    guard [15, 30, 60, 120].contains(minutes) else {
        throw NotificationServiceError.invalidReminderTiming
    }

    self.reminderMinutesBefore = minutes

    // Reschedule all notifications with new timing
    if notificationsEnabled {
        try await refreshNotificationQueue()
    }
}
```

private func handleDeeplink(_ url: URL) {
    // Handle notification deeplinks
    // Format: jab-tracker://dose/log?scheduledDoseId=<UUID>
    guard url.scheme == "jab-tracker" else { return }

    switch url.host {
    case "dose":
        handleDoseDeeplink(url)
    default:
        logger.warning("Unknown deeplink host: \(url.host ?? "nil")")
    }
}

private func handleDoseDeeplink(_ url: URL) {

## Learnings & Knowledge Capture

### 2025-10-31 Session Learnings

#### Technical Patterns → system-patterns.md

**SpringBoard App Deletion for iOS Permission Reset**
- **Problem**: iOS provides no API to programmatically reset notification permissions between E2E tests
- **Solution**: XCUITest SpringBoard automation to delete and reinstall app before each test
- **Pattern**: In setUp(), activate SpringBoard, long-press app icon, tap "Remove App", confirm deletion alerts
- **Critical Timing**: Must wait for icon to be "hittable" (`sleep(1)`) before long press to avoid "not hittable" errors
- **Reliability**: This is the ONLY reliable way to reset iOS system-level notification permissions for testing

**Auto-Advancing Permission Screens**
- **Discovery**: System permission dialogs (notifications, HealthKit) auto-advance to next onboarding screen without Continue button tap
- **Pattern**: Both "Allow" and "Not Now" buttons automatically advance flow - no Continue button needed in test helpers
- **Impact**: Reduced 5-hour debugging session to simple fix - removed incorrect Continue button taps
- **Best Practice**: When implementing onboarding permission flows, understand which screens auto-advance vs require explicit Continue

**E2E Test Scrolling Patterns for Below-Fold Content**
- **Problem**: Settings screen notification section below fold - tests couldn't find reminder picker
- **Solution**: Simple `app.swipeUp()` after Settings loads to access below-fold content
- **Anti-Pattern**: Checking if element exists before scrolling adds unnecessary complexity
- **Best Practice**: For known below-fold content, just swipe up directly - simpler and more reliable

#### Technology Insights → tech-context.md

**XCUITest SpringBoard Automation API**
- **Bundle Identifier**: `XCUIApplication(bundleIdentifier: "com.apple.springboard")` accesses iOS home screen
- **App Icon Access**: `springboard.icons["AppName"]` finds app icon on home screen
- **Long Press Duration**: `appIcon.press(forDuration: 1.3)` enters jiggle mode for deletion
- **Alert Handling**: Multiple confirmation dialogs ("Remove App", "Delete App", "Delete") require sequential handling
- **Timing Requirements**: 1-2 second waits between actions ensure UI state transitions complete

**iOS Notification Permission Test Requirements**
- **Permission State Persistence**: Notification permissions persist across app launches even with `--reset-app-data` flag
- **UserDefaults vs System Permissions**: UserDefaults can be cleared, but iOS system permissions cannot
- **Test Isolation**: Each notification E2E test must delete/reinstall app to ensure clean permission state
- **Duration Impact**: App deletion adds ~5-10 seconds per test, acceptable trade-off for permission reset reliability

### Technical Patterns → system-patterns.md

**AppServices Coordinator Pattern**
- **Problem**: NotificationService requires dependency injection (ScheduleService, ModelContext), preventing direct singleton usage
- **Solution**: Created AppServices.swift as centralized service coordinator with lazy initialization
- **Pattern**: Singleton coordinator provides access to services requiring ModelContext once initialized
- **Usage**: `AppServices.shared.initialize(with: modelContext)` in ContentView, then access via `AppServices.shared.notificationService`
- **Benefits**: Maintains singleton-like convenience for SwiftUI views while enabling proper dependency injection

**Debug-First E2E Testing Excellence**
- **Anti-Pattern**: Assuming SwiftUI element accessibility identifiers without verification leads to timing issues
- **Best Practice**: ALWAYS use `TestUtilities.debugElements()` before writing element selectors
- **Example**: Tests assumed `app.tabBars.buttons["Dashboard"]` existed, actual element was `app.scrollViews["dashboard-scroll-view"]`
- **Impact**: Debug-first approach solved 3 failing E2E tests in single session, all tests now passing reliably

### Technology Insights → tech-context.md

**UserDefaults for Notification Settings Persistence**
- **Decision**: Use UserDefaults instead of SwiftData for notification preferences
- **Rationale**: Device-specific settings (not synced), simple key-value storage, faster access, iOS platform conventions
- **Implementation**: NotificationService+Persistence.swift extension with saveState()/loadState() methods

**SwiftUI @ObservedObject with AppServices**
- **Pattern**: `@ObservedObject private var appServices = AppServices.shared` in SettingsView
- **Reason**: AppServices is ObservableObject, not @Observable, requires @ObservedObject property wrapper
- **Integration**: Binding to nested service properties: `Binding(get: { service.property }, set: { service.property = $0 })`
